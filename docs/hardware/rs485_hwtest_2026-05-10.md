# RS485 Hardware Test 2026-05-10

## Context

Hardware under test:

- ESP32-C6
- automatic TTL-RS485 module
- TAP powered from 24 V
- ESP powered from a 5 V DC/DC converter on the same 24 V supply
- CCA disconnected
- current firmware wiring: GPIO20 = RX, GPIO19 = TX
- bus speed: 38400 8N1

The firmware was temporarily replaced by a minimal raw UART hardware test build:

- firmware version: `2026.05.10.7-hwtest`
- USB serial enabled with `CDCOnBoot=cdc`
- no normal openTAPtoX state machine
- no parser requirement for counting RX data
- raw RX bytes counted and logged as hex
- pin modes:
  - mode A: RX=19, TX=20
  - mode B: RX=20, TX=19

Later hardware work established mode B as the active ESP32-C6 wiring and showed
that common ground between the ESP/RS485 side and TAP bus is required. The
current controller can run without the original Tigo CCA connected.

## Test Frames

Enumeration start frame:

```text
00 FF FF 7E 07 00 00 00 14 37 7E 01 92 66 12 35 06 1A 7E 08
```

Normal `0x0148` poll frame copied from working captures:

```text
00 FF FF 7E 07 12 08 01 48 00 01 00 00 04 E7 0D 7E 08
```

Reference response seen in known-good captures starts with:

```text
92 08 01 49 ...
```

## Observed Results

Mode A, `0x0014` enumeration loop:

- TX frames logged repeatedly
- `raw_rx_bytes_total=0`
- no TAP response

Mode B, `0x0014` enumeration loop:

- TX frames logged repeatedly
- one raw byte observed: `00`
- no valid-looking TAP response

Mode A, `0x0148` poll loop:

- `tx_poll0148_count=19`
- `raw_rx_bytes_total=0`
- no TAP response

Mode B, `0x0148` poll loop:

- `tx_poll0148_count=21`
- `raw_rx_bytes_total=1`
- `last_rx_hex=00`
- no `0x0149` TAP response

## Interpretation

The TAP did not visibly respond to either the enumeration start frame or the
normal `0x0148` poll frame in either pin mode.

The single `00` byte seen in mode B appeared exactly at transmit time and is
most likely echo, bus noise, or an electrical artifact rather than a TAP reply.

Because the `0x0148` frame was taken from working captures and should provoke
`0x0149` traffic on a known-good bus, the current working assumption is that the
RS485 hardware path is faulty. The RS485 converter module is the primary suspect.

Recommended next check:

- replace the RS485 converter module
- verify TX bytes on A/B with a second USB-RS485 sniffer
- inject a known byte sequence from a second adapter and confirm that the ESP
  raw RX counter increases with the expected hex data
